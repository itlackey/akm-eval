The first release of akm-eval. Every run made with it records version 0.2 for the collector and the scorer of every eval, in the manifest of its `summary.json`.

## What it brings

A run is split into three parts, so each kind of change invalidates only what it affects:
- **A scorer fix or a relabelled case** invalidates no run. Stored runs are scored again from their raw outputs (`scripts/rescore`), and `scripts/compare` and the matrix do this by themselves.
- **A changed case** is left out of a comparison and named.
- **A change to what akm is asked** (the collector) raises that eval's collector version. CI fails until the version is raised, and comparisons refuse two collector versions unless the collector is the treatment.

Versions are `MAJOR.MINOR`. A later release changes no version by itself: a part changes version only when its files change, so runs of two releases compare wherever their parts are the same.

README.md, "How results stay comparable", has the rules, and MEASUREMENT_CHANGELOG.md lists, eval by eval, what changed against results made before this release. Those older results compare only as exploratory.

## After upgrading

### 1. Make your private and custom test sets again

**Why.** Every `generate` script now writes, in the set's `generated.json`, a digest of its own code (with `lib/rewrite`) and of the public cases it read. `run` checks both before it calls akm. A set made before 0.2 has no such digest, so a run on it stops with a message like this one, and nothing runs:

```
the private assets cannot be used: ... Make them again with: ./generate-assets --only reflect
```

**Which sets.** The rewrites that `./generate-assets` makes in `private/<eval>/`, used by `--corpus custom`, `--corpus all` and the old `--corpus private`:
- agent-ab, bakeoff, consolidate, distill, extract, judge-gate, nightly, reflect, retrieval;
- benchmarks/longmemeval;
- benchmarks/terminal-bench, whose custom corpus reads the retrieval rewrite, so make retrieval's again.

These are not affected:
- public runs;
- your own notes, a folder given with `--cases` or `private/promotion/own`;
- the train split of benchmarks/skillret.

**How.**

```
./generate-assets                              # every eval, with the seed in private/seed
./generate-assets --only reflect,distill       # only the evals you run on a custom set
```

- **The seed.** It keeps `private/seed`, so the set is made from the same seed. The text can still differ from the old set, because the rewrite changed. Results on an old set compare only as exploratory, so run your baselines again on the new one.
- **corpus.json.** Each set also gets `private/<eval>/corpus.json`, which says it is a rewrite and not private. A `"private": true` you set there is kept.
- **Your own notes need nothing.** A folder you give with `--cases` and no `corpus.json` is treated as private, so it runs only with a model whose line in `models.json` says `"private": true`. To run it with other models, put `{ "kind": "own", "private": false }` in its `corpus.json`.

### 2. The first matrix run after upgrading runs every row again, once

**Why.** A matrix stage skips a row only when the row's fingerprint, stored in its `state.json`, is the same as now. In 0.2 the fingerprint is made differently:
- an eval's code counts as its collector version and digest from `MEASUREMENT.lock`;
- the case files count by what each case presents to akm, so a relabelled case no longer runs a row again.

No row in a results folder made before 0.2 matches, so the first `--stage screen` or `--stage confirm` on that folder runs each of its rows once more. The stage says what changed for each row. It costs what the first runs cost: the same model calls and the same time.

**What to do.**

```
scripts/matrix/run MATRIX.json --stage screen --dry-run       # see what would run
scripts/matrix/run MATRIX.json --stage screen                 # run it in the same folder; the old logs stay
scripts/matrix/run MATRIX.json --stage screen --out NEW_DIR   # or start a clean results folder
```

Results from before 0.2 have no manifest, and compare and the matrix treat them only as exploratory, so a re-run is needed for a real verdict in any case.

**From then on**, a scorer fix or a relabelled case runs no row again: the decision scores the stored results again, in memory. A row still runs again when:
- its eval's collector version changes;
- a case's input changes;
- the akm changes;
- an endpoint changes.

The changes are in #76.
