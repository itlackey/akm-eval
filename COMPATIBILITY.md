# Which akm each eval works with

akm is not in this repository. Every eval and benchmark that uses it runs the `akm` command line as a subprocess, from `AKM_BIN` or `PATH`, and reads what it prints. So the contract between an eval and akm is a set of command lines, JSON fields and a few texts, and nothing but this file says what they are. The unit tests run against fake akm scripts that print the shapes the eval expects, so they pass whatever akm does. `scripts/smoke` runs the evals against a real akm, nightly in CI (see "What has been run against a real akm").

The akm range of a row is what the eval is written for and what its README says. A floor marked *enforced* stops the run on an older akm. A floor marked *documented* is only in the README. No eval enforces a ceiling. "Last run on" is the release of the run its README records, or "none recorded" with the release the eval was built on. The one figure from a release above 0.9.26 is the timing of consolidate's pool run, on 0.9.30.

## Common to every eval that runs akm

- **The command line.** `--format json` is added to every command that does not already have it. akm's output contract says the top-level keys of the JSON and the error envelope `{ ok: false, error, code?, hint? }` are stable, and that exit codes are 0 success, 1 not found, 2 usage, 70 internal, 75 transient and 78 configuration. The evals show the `error` of that envelope in a row. The few places that read a text of akm are in the last column of the table.
- **The version.** `akm --version` is read for the first `x.y.z` (with a pre-release tag) it prints. A pre-release 0.10 build still prints a 0.9.x version, so the evals also record `akm_bin` and `akm_build` (`git describe --always --dirty` of the checkout that `AKM_BIN` runs from), and the kept semantic index is keyed on them.
- **The sandbox.** Every run gets its own `AKM_BUNDLE_DIR`, `AKM_CONFIG_DIR`, `AKM_DATA_DIR`, `AKM_CACHE_DIR` and `AKM_STATE_DIR` (Internal) and `XDG_*` folders in a temp folder, and none of the caller's `AKM_*` settings.
- **The config the evals write.** `configVersion` `0.9.0`, `semanticSearchMode`, `registries`, `embedding.localModel` and `.queryTimeoutMs`, one `engines.<name>` of `kind: llm` and `provider: openai` (`endpoint`, `model`, `apiKey` as `$MODEL_API_KEY`, `timeoutMs`, `temperature`, `enableThinking`), `defaults.llmEngine` and `.improveStrategy`, and `improve.strategies.<name>` with `engine`, `processes` and `sync`. akm marks the `improve.strategies.*.processes.*` keys Experimental: they "may be added, renamed, or dropped in any 0.9.x or 0.10.x release".
- **The stability policy.** akm ships `STABILITY.md` in its npm package. In 0.9.26 it lists `index`, `info`, `search`, `curate`, `feedback`, `bundle create`, `config set` and `proposal list` as Stable; `improve`, `proposal show`, `proposal drain` and `proposal extract` as Evolving ("output JSON keys are stable; CLI flags may add options or tighten validation"); and the `--shape` projection, the `improve` tuning config and the environment variables `AKM_EMBED_DETERMINISTIC`, `AKM_CLAUDE_PROJECTS_DIR` and `AKM_STATE_DIR` as Experimental or Internal. It says to use `akm` commands and not SQL against `state.db`, which is what `evals/promotion` does.

## What has been run against a real akm

`scripts/smoke` starts a stub model that answers `{}` to every call and runs each eval that drives akm once, on one case, with `--limit 1 --label smoke`. It asserts only that the run ends and writes a `summary.json`, and prints what the first row says. A model that answers `{}` makes the cases error or come out empty, so it says nothing of the scores. It does show that akm still takes the commands and prints JSON the eval can read, because an eval that cannot get as far as the model prints a WARN and `--strict` fails on it.

| Run | akm | Result |
|---|---|---|
| 2026-10-11, `npm i -g akm-cli@0.9.26`, Node 22 | 0.9.26 | `retrieval`, `judge-gate`, `reflect`, `distill`, `consolidate`, `extract` and `nightly` ran to a `summary.json`, and each but retrieval (which calls no model) reached the stub. `judge-gate` got `score: -1` with `reviewNeeded` and the two reason texts above, for a reply of `{}` and for an HTTP 500. `promotion` was not run: it needs akm's embedding model from huggingface.co, which the machine could not reach. A probe on the same akm, of what promotion relies on, found the ten columns of `proposals` and the two of `events` where the eval looks for them, `proposal list --status pending` listing the three rows written there, and the flags `--judgment`, `--strategy`, `--yes` and `--promote` in the help of `proposal drain`. The drain and the judge were not run. The host side of `benchmarks/terminal-bench` (`bundle create`, `index --full`, `info -q`) counted 259 assets in `corpus/library`, the number its README gives. |

The CI job `akm-smoke` (`.github/workflows/akm-smoke.yml`) repeats this every night on the release pinned in `lib/harbor/harbor.ts` and on the latest release, and on demand.

Not run against a real akm: the drain of `evals/promotion`, anything on 0.10, `evals/distill`'s `lesson-update` class, a checkout of akm by `--akm`, the semantic search of any eval, the Harbor evals (they need Docker) and the two benchmarks that download a dataset (`longmemeval`, `skillret`).

## When a new akm ships

1. Run `scripts/smoke/run` with it: `scripts/smoke/run --akm "bun ~/code/akm/src/cli.ts" --strict`. Read what the first row of each run says. `evals/promotion` is the one most exposed to a change, since it writes into akm's tables: after the smoke, run it once with a real model and watch for its schema message.
2. Read the new `STABILITY.md` and the CHANGELOG for the surfaces in the table.
3. Run each eval you track with `--repeat 3` against the old and the new akm and compare with `scripts/compare/run`. An `akm_version` that did not change does not mean the build did not: read `akm_build`.
4. Change this file: the range, the last release each row was run on, and any command or field that moved.

The versions of akm named in this repository are in `lib/harbor/harbor.ts` (`PINS`, for the Harbor evals and the nightly smoke), the `MIN_AKM` constants of `evals/judge-gate`, `evals/reflect`, `evals/nightly` and `evals/extract`, the `Written for` and `Needs akm` lines of the eval READMEs, and this file.
