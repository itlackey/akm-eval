# Which akm each eval works with

akm is not in this repository. Every eval and benchmark that uses it runs the `akm` command line as a subprocess, from `AKM_BIN` or `PATH`, and reads what it prints. So the contract between an eval and akm is a set of command lines, JSON fields and a few texts, and nothing but this file says what they are. The unit tests run against fake akm scripts that print the shapes the eval expects, so they pass whatever akm does. `scripts/smoke` runs the evals against a real akm in two modes, nightly in CI (see "What has been run against a real akm").

The akm range of a row is what the eval is written for and what its README says. A floor marked *enforced* stops the run on an older akm. A floor marked *documented* is only in the README. No eval enforces a ceiling. "Last run on" is the release of the run its README records, or "none recorded" with the release the eval was built on. The one figure from a release above 0.9.26 is the timing of consolidate's pool run, on 0.9.30.

## Common to every eval that runs akm

- **The command line.** `--format json` is added to every command that does not already have it. akm's output contract says the top-level keys of the JSON and the error envelope `{ ok: false, error, code?, hint? }` are stable, and that exit codes are 0 success, 1 not found, 2 usage, 70 internal, 75 transient and 78 configuration. The evals show the `error` of that envelope in a row. The few places that read a text of akm are in the last column of the table.
- **The version.** `akm --version` is read for the first `x.y.z` (with a pre-release tag) it prints. A pre-release 0.10 build still prints a 0.9.x version, so the evals also record `akm_bin`, `akm_build` (`git describe --always --dirty` of the checkout that `AKM_BIN` runs from) and `akm_build_fingerprint` (a sha256 of the uncommitted changes of that checkout, null when clean), and the kept semantic index is keyed on them.
- **The summary.** Every `summary.json` records `status` (`complete` or `aborted`), `aborted_reason` and `harness_sha256`, a digest of the eval's own code and the shared `lib/` it runs.
- **The sandbox.** Every run gets its own `AKM_BUNDLE_DIR`, `AKM_CONFIG_DIR`, `AKM_DATA_DIR`, `AKM_CACHE_DIR` and `AKM_STATE_DIR` (Internal) and `XDG_*` folders in a temp folder, and none of the caller's `AKM_*` settings.
- **The config the evals write.** `configVersion` `0.9.0`, `semanticSearchMode`, `registries`, `embedding.localModel` and `.queryTimeoutMs`, one `engines.<name>` of `kind: llm` and `provider: openai` (`endpoint`, `model`, `apiKey` as `$MODEL_API_KEY`, `timeoutMs`, `temperature`, `enableThinking`), `defaults.llmEngine` and `.improveStrategy`, and `improve.strategies.<name>` with `engine`, `processes` and `sync`. akm marks the `improve.strategies.*.processes.*` keys Experimental: they "may be added, renamed, or dropped in any 0.9.x or 0.10.x release".
- **The stability policy.** akm ships `STABILITY.md` in its npm package. In 0.9.26 it lists `index`, `info`, `search`, `curate`, `feedback`, `bundle create`, `config set` and `proposal list` as Stable; `improve`, `proposal show`, `proposal drain` and `proposal extract` as Evolving ("output JSON keys are stable; CLI flags may add options or tighten validation"); and the `--shape` projection, the `improve` tuning config and the environment variables `AKM_EMBED_DETERMINISTIC`, `AKM_CLAUDE_PROJECTS_DIR` and `AKM_STATE_DIR` as Experimental or Internal. It says to use `akm` commands and not SQL against `state.db`, which is what `evals/promotion` does.

## What has been run against a real akm

`scripts/smoke` runs each eval that drives akm once, on one case (`--limit 1 --label smoke`), against a stub model, in two modes. The startup mode answers `{}` to every call. It asserts only that the run ends and writes a `summary.json`, and prints what the first row says. It shows that akm takes the commands and prints the JSON the eval reads before it calls the model. It shows no proposal, lesson, memory or verdict, because every model-backed case may error and the run still passes. `retrieval` calls no model, so `--strict` fails when `search` or `curate` returns no ref for its one query. The contract mode (`scripts/smoke/run --contract`) answers each call with a reply that fits the schema akm sends, with canned replies where akm turns that down. It fails unless each eval reaches the outcome it counts as its work: a reflect proposal, a distilled lesson queued for review, an extract memory saved, a judge verdict, a pair retired and staged (consolidate, and the nightly's drain), a promotion accepted. It then answers text that is not JSON and requires the eval's outcome for an unreadable reply. It uses one case per eval and one reply for all cases. It does not run the night's reflect, distill, exact-fix and validation processes, and it never asserts that a case came out right, so it shows that an eval can reach and read a success on a release, not that its checks tell a good model from a bad one.

The CI job `akm-smoke` repeats this every night and on demand: the contract mode on the release pinned in `lib/harbor/harbor.ts` (a leg that must pass) and the startup mode with `--strict` on the latest release (advisory, `continue-on-error`). ## When a new akm ships

1. Run `scripts/smoke/run --contract` with it, then `--strict` (for a checkout, add `--akm "bun ~/code/akm/src/cli.ts"` to each). Read what each run says. A canned reply that was never used means akm sent a request the contract was not written for. `evals/promotion` is the one most exposed to a change, since it writes into akm's tables: after the smoke, run it once with a real model and watch for its schema message.
2. Read the new `STABILITY.md` and the CHANGELOG for the surfaces in the table.
3. Run each eval you track with `--repeat 3` against the old and the new akm (`--akm`, or `AKM_BIN`), with the same model, the same config and the same cases, from a commit of this repository that is not `-dirty`, and compare the two sets with `scripts/compare/run --repeats <old label> --against <new label> --treatment build`. For one run each, `scripts/compare/run OLD NEW --treatment build`. The treatment is what the comparison changes, here the akm; without `--treatment build` the tool refuses a different `akm_version`, `akm_build` or `akm_bin`. Everything outside the treatment must be the same in every run, so it also refuses a different model or engine setting, akm config, `assets_sha256` or eval commit, and a report from summaries that lack the evidence for one of those (the cases, the config, the engine, a clean commit), or from a run that did not complete, is labelled exploratory and is not a conclusion. The Harbor evals have no per-case reading: compare them with a matrix whose rows name the two releases in `--akm` (README, "Compare akm builds"), which applies the same rules. An `akm_version` that did not change does not mean the build did not: read `akm_build`.
4. Change this file: the range, the last release each row was run on, and any command or field that moved.

The versions of akm named in this repository are in `lib/harbor/harbor.ts` (`PINS`, for the Harbor evals and the nightly smoke), the `MIN_AKM` constants of `evals/judge-gate`, `evals/reflect`, `evals/nightly` and `evals/extract`, the `Written for` and `Needs akm` lines of the eval READMEs, and this file.
