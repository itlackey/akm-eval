# retrieval

Does akm search put the assets an agent needs at the top?

akm indexes a library of assets: skills, knowledge notes, commands, agents, workflows and scripts. An agent finds them with `akm search`, or asks `akm curate` for a short list for its task. This eval gives akm queries over two public collections. It scores the first 10 results of both commands against graded judgments of which assets answer each query, with akm's keyword search and, in a full run of the public and private collections, with its semantic search too.

- `library`: 111 task queries and 25 non-task inputs over the public library in `corpus/library`.
- `books`: 51 task queries over 93 assets in three domains: cooking, law and tax, and anatomy and first aid. The judgments come from an earlier experiment. Besides grades, they name assets that must never outrank a relevant one, such as an asset that holds an out-of-date figure.

Each collection is scored on its own, never pooled with another. A third corpus, `own`, runs a labelled set of yours.

No model service is called when you run the eval. The semantic search is a small embedding model that akm runs inside its own process. A judge model graded the library's assets once, to make `assets/qrels.jsonl`. The books' judgments were made by hand for the earlier experiment. See "Make or extend the judgments" below.

## Run

```
evals/retrieval/run --corpus public
evals/retrieval/run --corpus private
evals/retrieval/run --corpus own
evals/retrieval/run --corpus all
```

- `--corpus` picks the assets. `public` runs the library and the books, each on its own, and prints them side by side. `private` runs their private copies. `own` runs your own set, with keyword search only unless `--semantic on`: see "Run your own set". `all` runs public and private, and prints the public and the private result of each collection side by side, never as one number.
- `--limit N` runs N queries of each collection, in the task and non-task proportion of its whole set. Use it to check a setup. It scores keyword search only unless `--semantic on`, and takes under a minute.
- `--repeat N` runs each collection N times into `<label>-r1-<collection>` to `<label>-rN-<collection>` folders and writes the `min`, `max` and `mean` of each metric to `<UTC date>-<label>-<collection>-repeat-summary.json` beside them. Retrieval has no model, so the spread is of the timings; the semantic index is kept between the runs. See "Repeat a run" in the root README.
- `--label NAME` names the results folders, `<UTC date>-<label>-<collection>`. The default label is `akm-<version>`.
- `--semantic on|off|auto` decides whether the semantic search is scored. `auto`, the default, scores it in a full run of the public and private corpora, and not with `--limit` or for `own`. `on` scores it for any run, `--limit` and `own` included: for a large own library that embeds every asset, which took 52 minutes for about 24,000 assets the first time and is kept for the next run. `off` never scores it. The summary records the flag as `semantic_flag`.
- `--akm COMMAND` runs the akm that `COMMAND` starts, such as `--akm "bun ~/code/akm/src/cli.ts"`, in place of `AKM_BIN` or the akm on `PATH`.

The private run reads `private/retrieval/assets/`. Make it first with `./generate-assets --only retrieval`. The run stops with an error when it is missing, and when it was made from public files that have changed since: the library, the queries or the qrels (`label` appends to them). `generated.json` in that folder says what the assets were made from (the seed, a digest of those public files, and a digest of the code that rewrote them), and the error says to make them again. The own run reads `private/retrieval/own/`, and stops with an error that says how to make a set when the folder holds none.

Each run writes two files for each collection to `evals/retrieval/results/<UTC date>-<label>-<collection>/` (the collection is `library` or `books`), or to `private/retrieval/results/` for the private corpus and for `own`:

- `summary.json`: the metrics of the four columns (the two keyword ones when the run has no semantic search), how many queries were scored, the akm version and build (`akm_bin`, `akm_build`), the search mode akm reported for each index, the embedding model, whether the semantic index was built for the run or kept from an earlier one (`semantic_index`) and which akm built it (`semantic_index_built_by`: its version, `akm_bin`, `akm_build` and the time akm says it built the index), what `--semantic` said (`semantic_flag`), how long each index took, the corpus, the collection and the git commit. `errored` counts the failed calls of each column, and `timeouts` how many calls, in any column, were killed at their time limit of 120 seconds. A timeout is an errored call too. A slower akm shows there, and not as unexplained errors.
  It also says what the run was made from. `config` is the akm config the eval wrote for each index (`keyword` and, when the run has one, `semantic`), with any key redacted, and `engine` the LLM engine of that config, which has no fields set because retrieval calls no model. `assets_sha256` is one digest over what the run was made from: the library akm indexed, the bundle mapping, the queries and the qrels. `assets` keeps the four digests it is made of, to tell which input two runs differ in: `library_sha256` is every file akm indexed, by its path from the library and the sha256 of its content (for a library of bundles, the files of each bundle that `bundles.json` names, by the bundle's name and wherever the bundle is, so a bundle that is a link to another folder, or is named by a path outside the library, counts); `bundles_sha256` is the mapping of `bundles.json`, `null` when the library has none; `queries_sha256` and `qrels_sha256` are the content of `queries.jsonl` and `qrels.jsonl`. `assets_sha256` is the sha256 of those four, in that order, one to a line, with `none` for no mapping. Editing, adding, removing or renaming an asset of the library changes `library_sha256` and so `assets_sha256`, in a run with a new semantic index, in one with a kept index, and in one with keyword search only, and `label` adding a grade changes `qrels_sha256`. They hold contents and paths from the library, so they are the same on every machine and in every checkout, and two runs with another `assets_sha256` searched another library or scored other judgments. For the private corpus `seed` is the seed of the rewrite that made the private assets (the one in `generated.json`), else the one in `private/seed`, else `null`. The public and own corpora have none: neither is made from a seed.
- `samples.jsonl`: one line per query, with what search and curate returned on each index, the grade of each result, the scores and how long each call took. A call that was killed at its time limit has `timed_out: true` and an error that says so.

## What it needs

[bun](https://bun.sh), and akm on `PATH` or named in `AKM_BIN`. No model service and no key. The network is used once, the first time a run builds a semantic index: akm downloads its embedding model, bge-small-en-v1.5 (133 MB, from the Hugging Face Hub), and the eval keeps it in `.cache/models/` at the root of the repository, which git ignores. Every later run, and every sandbox, reads it from there.

The eval copies the library into a temporary folder, gives akm its own config and folders there, and indexes it for keyword search, which takes under a second. It never reads or writes your akm bundle. The semantic index is kept between runs: see "The semantic index is kept between runs". akm 0.9.26 on a busy 12-core machine took 17 s to build the semantic index of the library's 259 assets and 5 s for the books' 93 (22 and 14 s in an earlier run, when the machine was busier), and 0.2 s to use a kept one. Then the eval makes four calls per query: search and curate, each on both indexes. A keyword call takes 0.2 to 0.3 s and a semantic one 0.7 s, because each akm process loads the model. The library's 136 queries took 4 minutes of calls and the books' 51 took 1.5, against a minute and half a minute with keyword search alone. A run of both collections took 6 minutes with a new semantic index and with a kept one, since indexing 350 assets takes 23 s. A library of several bundles (see "Run your own set") is not copied: akm indexes each bundle where it is, read only.

Keyword search is akm 0.9.26's default: the sandbox config has `semanticSearchMode: "off"`. The semantic index is built with `semanticSearchMode: "auto"` and `embedding.localModel` set to bge-small-en-v1.5, which is also akm's own default model. Semantic search in akm fuses its keyword ranking with the nearest vectors by reciprocal rank, so it is not vectors alone. akm answers a query with keyword search alone, `searchMode: "fts-fallback"`, when it cannot embed it in time (3 seconds by default, which 2 calls of 96 missed at eight at once on a busy machine). The sandbox allows ten minutes, and the eval still takes any answer that does not say `semantic` for a failed call. It also stops before the first query if the index does not hold an embedding of every asset, or if one semantic search does not say `searchMode: "semantic"`. A semantic call has to say it: an answer with another mode, or with none, is a failed call, so a build of akm that dropped the field could not pass keyword rankings off as semantic. A keyword call that does not say how it searched is taken as it comes.

## The semantic index is kept between runs

Embedding a library is most of the time a semantic run takes, so the eval keeps the index it built in `.cache/akm-index/retrieval-<corpus>-<collection>/`, such as `retrieval-public-library/`, which git ignores, and the next run uses it as it is. The folder is akm's whole sandbox for that index, with the copy of the library in its bundle, because akm records the paths of what it indexed and indexes everything again when they move. It takes 11 MB for the library and 2 MB for the books.

A kept index is used again when akm, its embedding model and the folder are the same and every file of the library (of the bundles `bundles.json` names, for a library of bundles) has the content it had when the index was built. The same akm is the same printed version, the same command, the same git build and the same uncommitted changes (`akm_version`, `akm_bin`, `akm_build` and `akm_build_fingerprint` of the summary). A different build, such as a branch you checked out, makes the eval say `the index ... cannot be reused: ... it was built by akm X build A (...), and this run is akm X build B (...)` and build a new index. `state.json` in the index's folder records which akm built it (`version`, `akm_bin`, `akm_build` and `builtAt`), and `summary.json` has the same as `semantic_index_built_by`, beside `semantic_index`. A file that changed, is gone or is new makes the eval build a new index from nothing, and say so. It never updates an index, because akm 0.9.26 does not update an index to what a new one is:

- An asset that was changed or removed stays in the row count and the token totals of the keyword index, which is a contentless FTS5 table, so every BM25 score is a little off from then on. Over the 6,006 skills of the skillret benchmark, 10 changed skills gave 37 of 400 queries another top 15, 10 removed skills gave 25, and 200 changed skills gave 325. Skills that were added did not change one.
- `akm index --full` on an index that exists counts every asset twice.
- Updating the index of the public library, with no file changed, switched 17 of its 259 assets to their other file and embedded 15 of them again, and 89 of its 136 queries ranked otherwise in one run, 37 of 60 in another. Two files of the library claim each of those 17 refs, such as `knowledge/skills/x/references/a.md` and `skills/x/references/a.md`. akm indexes one of the two, and an update can swap it for the other ([akm#1050](https://github.com/itlackey/akm/issues/1050)). The ids stay the same.
- The books' index of 93 assets shows what an update does well. A changed file was the only asset re-embedded (2.6 s for the update, against 22 s for a new index) and 50 of the 51 queries ranked as on a new index of the same files, with nDCG@10 0.9215 against 0.9214. A new file was the only asset embedded, and all 51 queries ranked the same.

So a run on a kept index gives the rankings of the run that built it: the cold and the warm runs of the public collections returned the same results for every query, on all four columns. Before it uses a kept index the eval asks akm what the index holds (`akm info`): the number of assets and the time it was built must be those that the build recorded, and it must hold embeddings. When it does not, the eval says so, builds a new index, and `summary.json` has `"semantic_index": "rebuilt"`. It is `"warm"` for an index that was kept and `"cold"` for one that was built because none was kept. What akm logged of the searches of the earlier run is deleted first, so a run starts with no search history. One run uses an index at a time: a second run stops and says which file to remove if no run is using it.

akm lists the files of a bundle that is inside a git repository with `git ls-files`, which leaves out what the repository ignores, and the repository ignores `.cache/`. An index there would hold no asset, so the eval has git stop looking for a repository at the index's folder, and akm walks the bundle itself. To start over, delete `.cache/akm-index/`.

## What it asks akm

For each query: `akm search --limit 10` and `akm curate --limit 10`, on the keyword index and on the semantic one. curate returns 4 by default. The eval asks for 10, so both commands are scored on the same cut-offs.

A result that names a section of an asset (`ref#section`) counts as the asset, at its first place. The assets that a curate hit links to (`supportRefs`) are not results and are not counted.

curate runs one search and attaches a preview and run details to each hit. A reranker can reorder its candidates first, but it is off by default and the eval leaves it off. So curate returns the same assets in the same order as search, on either index. It differs in one way: it abstains on input that is a harness envelope, such as `<task-notification>...</task-notification>`.

## Read the results

Each metric is given for four columns: `search` and `curate` on the keyword index, and `semantic_search` and `semantic_curate` on the semantic one. A run with `--limit`, and the own corpus, have the two keyword columns only, unless `--semantic on` asks for the other two. A task query is scored when at least one asset has grade 2 or 3 for it ("relevant"). The scores are means over those queries. A task query with no relevant asset is not scored. It is counted, and reported with the abstentions.

| Metric | Meaning |
|---|---|
| `ndcg_10` | nDCG over the first 10 results. An asset of grade g gains 2^g - 1, discounted by log2 of its rank + 1, against the best order of everything graded for the query. A result nobody graded counts as not relevant. |
| `ndcg_10_condensed` | nDCG over the judged results alone: the results nobody graded for the query are taken out of the list and the rest move up, against the same ideal order. `ndcg_10` is penalised for surfacing assets nobody judged, and this is not. It is never below `ndcg_10`, and the two are equal when `judged_10` is 100%. Read the pair as bounds. A gap between them that grows from one run to the next is the unjudged results: run `label --from` on the run before you compare. |
| `p_5` | The share of the first 5 places that hold a relevant asset. Fewer than 5 results leave places empty. |
| `success_5` | The share of queries with a relevant asset in the first 5. |
| `mrr` | One over the rank of the first relevant asset, within the first 10. 0 when there is none. |
| `recall_10` | The share of the query's relevant assets that are in the first 10. |
| `judged_10` | The share of the results among the first 10 that someone graded for the query, as a mean over the queries that returned any result. A query that returned nothing has none and is left out (it counted as 100% before). This is not a quality score. See "Notes". |
| `banned_above` | Only where the qrels ban assets, as the books' do. The share of those queries in which a banned asset is among the first 10 and ranks above a relevant one, the last of them. A relevant asset that is not among the first 10 ranks below every result, so any banned asset that is returned ranks above it, and a relevant asset that is missing counts as banned-above. Lower is better. |
| `banned_above_first` | The same share, for a banned asset that ranks above the first relevant asset. A missing relevant asset does not count here unless every one is missing. The gap to `banned_above` is the queries where only a relevant asset that is missing puts a banned one above. |

Non-task inputs are chit-chat, notifications, log lines and status updates, where the right result is nothing. `abstention.non_task` is how many of them got no result from akm at all, for each column. `abstention.no_answer` is the same count for the task queries that have no relevant asset. A semantic search always has nearest vectors to return, so only a command that abstains by rule, curate on a harness envelope, can return nothing on the semantic index.

A call that fails, such as a timeout, or a semantic call that akm answered with keyword search or without saying how it searched, is counted in `errored` and left out of that column's numbers. A call that ran into its time limit is also counted in `timeouts`, and its row has `timed_out: true`. When a semantic call failed, the collection's summary says `status: "aborted"`, with the count in `aborted_reason`, and the run exits with 1.

When the qrels hold grades of more than one judge or prompt (`judge` and `prompt_sha256` of their rows: see "Make or extend the judgments"), the run warns once, on stderr, that grades of different judges do not mix cleanly. Rows made before `label` wrote a judge count as one more judge once any row records one: they were graded by someone, and the new grades sit beside theirs. A set where no row records a judge, as the library's was before `label` wrote them, is not a mix, so the warning starts with the first grade that `label` appends to it.

## Assets

- `assets/queries.jsonl`: 111 task queries and 25 non-task inputs. Each has an id, the query and a kind. A task query also has the assets the author expected to answer it.
- `assets/qrels.jsonl`: the grade, 0 to 3, of each asset a judge model was shown for each task query, and since `label` writes them, who graded it and from what: the judge, a digest of the prompt, the day and a digest of the asset.
- `assets/spotcheck.jsonl`: 40 random pairs from the qrels that the author graded without seeing the judge's grade, next to the judge's.
- `assets/books/`: `library/`, the 93 assets, `queries.jsonl`, 51 task queries, and `qrels.jsonl`, 179 judgments: 80 relevant assets, graded 3 or 2, and 99 banned ones, grade 0. They come from the earlier experiment E6, which built them over three public books. The books themselves are not used. The three licences and the attribution are in `../../NOTICE`.
- `assets/README.md`: how the queries were written, the mix of kinds, how the judgments were made, the judge model, the date and how well the judge agrees with a second model (no person graded the pairs), how the books' judgments were turned into grades, and the format of a set of your own. The assets carry a canary string: do not train on them.
- `private/retrieval/assets/`: `library/`, `queries.jsonl` and `qrels.jsonl`, the same set with names, tool names, hosts, ids, dates, numbers and versions rewritten from a seed by `lib/rewrite`, and `generated.json`. One rewrite run covers the library, the queries and the judgments, so a name changes the same way in all of them, and every grade is kept. akm keeps its name, and so does every other tool of the rewrite's list that the library tells a reader to run: a command on a line of a shell code block or in an inline `command with arguments` (`uv run`, `docker build`, `opencode auth login`). Terminal-bench hands this library to an agent that runs the real tools, and a renamed `akm` would be a tool that does not exist. `generate` finds them in the library, and today they are 22: akm, aider, anthropic, aws, azure, bun, claude, codex, copilot, docker, gcloud, gemini, groq, gutterpress, ollama, openai, opencode, openrouter, pipx, playwright, pnpm and uv. The other tools are renamed in the files, in the file names, in the queries and in the refs. With seed 20261011, 29 of the library's 245 graded refs change (89 when every tool is renamed), 1.6% of the library's words (3.5% when every tool is renamed) and 3.1% of its queries' (4.1%). These figures were counted before 24 copies of files were removed from the library, which has 237 graded refs now (see "Changes since the grading" in `assets/README.md`); the next `generate` run counts them again. Words are runs of letters and digits, counted at the same place in the text before and after the one rewrite run that `generate` makes of the library, the queries and the judgments. The mapping is `private/retrieval/map.json`. They are made by `generate` and never published. `generate` also checks them: every ref in the qrels and every expected asset must name an asset akm indexes in the private library, and every task query must keep its relevant assets. It makes everything in a folder beside the assets and moves it into place only when both collections pass, so a run that fails leaves the assets and maps of the run before as they were.
- `private/retrieval/assets/generated.json`: `{ "seed", "inputs_sha256", "rewrite" }`. `inputs_sha256` is one digest over the public files the assets were made from: every file of `corpus/library` and of the books' library, and the queries and qrels of both collections. `rewrite` is one digest over the code that rewrote them: `lib/rewrite/rewrite.ts`, `lib/rewrite/lexicon.ts` and `evals/retrieval/src/generate.ts`, which says which tools keep their names. `run --corpus private` recomputes both and stops when either differs, or when the file is missing, because the private assets are then the rewrite of a public set that no longer exists, or the work of a rewrite that has changed since (a new tool in the lexicon, a fix to the numbers, another pin). Any edit to those three files counts, a comment included. Make the assets again with `./generate-assets --only retrieval`. The seed is not compared with anything: `./generate-assets --seed N` makes assets from a seed other than `private/seed`, and the seed in this file is the one the assets were made from.
- `private/retrieval/assets/books/`: the same three for the books, made by the same `generate` run in a rewrite of their own, with the mapping in `private/retrieval/books-map.json`. The assets name few tools or people, so little changes: 3 words and 40 numbers, 0.65% of the words of the library, and none of the queries.
- `private/retrieval/own/`: your own set. See below.

Two groups, `ai-skills` and `print`, hold 59% of the graded rows and 60% of the relevant ones, and `coding` another 13%. ## Run your own set

```
evals/retrieval/run --corpus own
```

Put a labelled set of your own in `private/retrieval/own/` and run it like the others. It is scored with the same metrics, and its results go to `private/retrieval/results/`. Nothing in `own/` is published. The folder holds:

- `queries.jsonl` and `qrels.jsonl`, in the format that `assets/README.md` describes. A query whose `kind` is `nontask` (or `chitchat`, `notification`, `log` or `status`) is an input whose right result is nothing. Every other query needs grades in `qrels.jsonl`.
- `library/`: the folder akm should index, or a link to it. It is copied into the sandbox as one bundle, so the refs in `qrels.jsonl` are the refs `akm search` prints for it.
- `bundles.json`, only when `library/` is a folder of bundles: it names each bundle's folder and the akm adapter that reads it, such as `{ "notes": "akm", "site": "website-snapshot" }`. Each bundle is indexed where it is, read only, and nothing is copied, so a link to a large frozen snapshot works. akm prints their refs as `<folder>//<path>`, so the qrels use those. Name the adapter of each bundle: when akm picks one itself it can pick another than the one you mean, and index other assets.

The run stops with an error that says this when the folder holds no set in this format. When akm or the library changes and `judged_10` falls, `evals/retrieval/label --corpus own` grades the results that have no grade yet: see "Make or extend the judgments".

The own set is scored with keyword search alone, unless you pass `--semantic on`. Keyword search took 6 minutes for a set of about 24,000 assets: its library is large, and embedding it is slow. Semantic search was measured once on such a set, a frozen snapshot of about 24,000 assets with 362 queries, 292 of them scored (akm 0.9.26, 2026-10-06). nDCG@10 was 0.513 against 0.500 with keyword search, 0.013 higher with a 95% interval of 0.020 either way over the same queries, so the semantic search made no clear difference. Success@5 was 88.4% against 86.6% and Recall@10 0.334 against 0.322. Embedding the assets took 52 minutes at about eight assets a second, and the whole run 68 minutes against 6 with keyword search alone. With the index kept, a second run would take about 16 minutes, the queries alone: that is an estimate, not a measurement.

## Make or extend the judgments

```
evals/retrieval/label
evals/retrieval/label --limit 5
evals/retrieval/label --from evals/retrieval/results/2026-10-11-akm-0.9.26-library
evals/retrieval/label --corpus own
```

For each task query, `label` pools the top 10 of `akm search`, the top 10 of `akm curate`, the top 10 of a plain BM25 over the library files, and the assets the author expected. It asks a judge model to grade each pooled asset 0 to 3 that has no grade yet, and appends the grade to `assets/qrels.jsonl` as it arrives. Stop it at any time and run it again: a graded pair is not graded again, unless its asset changed since (see "Who graded what").

Set `JUDGE_BASE_URL`, `JUDGE_API_KEY` and `JUDGE_MODEL` in `.env`, for any OpenAI-compatible chat endpoint, or pick the judge with `--judge-model ID`, which wins over `JUDGE_MODEL`. An id that is a line of `models.json` (beside `.env`, copied from `models.example.json`) goes to that line's URL with the key held in its `api_key_env`. Any other id goes to the endpoint in `.env`, and a judge with no `JUDGE_BASE_URL` uses the model's endpoint: see "Pick the model and the akm build of a run" in the root README. `--akm COMMAND` runs another akm than the one on `PATH`. It sends two requests at a time. `--limit N` labels only the first N task queries. `--corpus` picks the set: `public` (the default) is the library in `corpus/library`, with the queries and judgments in `assets/`, and `own` is your own set in `private/retrieval/own/`.

### Pool a run: `--from`

The pool above is what akm's keyword search, curate and BM25 return, and the author's list. The semantic search, and any change of akm that surfaces other assets, returns results that nobody graded, and `ndcg_10` counts those as not relevant (the library's semantic `judged_10` was 71%). `--from RESULTS_DIR` pools a run instead:

```
evals/retrieval/run --corpus public
evals/retrieval/label --from evals/retrieval/results/<UTC date>-<label>-library
```

The pool of each task query is the first 10 results of every column in that run's `samples.jsonl` (search and curate, keyword and semantic), and the assets the author expected, each once. `label` asks akm for nothing but the listing of the library, and grades the pairs that have no grade yet. Run it, and `ndcg_10` of that run and of every later run covers what the semantic search returned. `RESULTS_DIR` has to be a run of the same corpus and collection: the library of the public corpus, or `own` with `--corpus own`. A run of the books or of the private copy is refused, because `label` does not grade them. A result that is not an asset of the library, as when the run was of another version of it, is left out and counted. With `--corpus own` the library has no listing, so `label` asks akm for each query again to learn what it says of an asset, and grades a result of the run only when akm returns it now. A result that only the semantic search returned cannot be looked up there, and is left out.

### Who graded what

Each row `label` appends has `judge` (the model), `prompt_sha256` (a digest of the prompt text, its layout and the 16,000-character window), `date` (the UTC day) and `asset_sha256`. The last is a digest of the asset as the judge read it: its ref, its front matter and the text after it up to the window. It is of the file, not of what akm says of it, so another akm gives the same digest, and a change past the window, which the judge does not see, does not change it. The four fields are optional: the 1,521 rows made before `label` wrote them have none, and `run` and `parseQrels` read them as before. Who graded them is not recorded, and the first judge that `label` adds is a second one beside them: see below.

A pair whose last row has a digest that is not the asset's now is graded again, when its query is among the ones labelled, and the new row follows the old: a pair that appears twice keeps its last grade. The old row stays in the file as history. A pair from before the digests has none to compare, so it is never graded again; to grade it with the current text, delete its rows from `qrels.jsonl`. `generate` and the private qrels carry `judge`, `prompt_sha256` and `date` over, and leave the digest out, since it is of the public text.

Use one judge for all the grades of a set. `label` warns when the qrels hold the grades of another judge than the one it grades with, or grades that record no judge, and `run` warns once when they hold more than one judge or prompt, or one judge beside rows that record none. Both look at the last row of each pair, the grade in force: a pair that is graded again by the judge of the set no longer counts for the judge or the missing judge of its old row. To clear the warning on a set with rows that record no judge, stamp them with the judge that graded them, if it is known (the library's: see `assets/README.md`), or delete their rows and let `label` grade them again with the one judge. Neither is done for you.

The request is made for a local server such as llama.cpp: temperature 0, room for 2000 tokens, every spelling of "no visible thinking", and a JSON schema for the reply. If the server refuses the schema, the request is sent again without it. A cloud endpoint can answer 400 to the thinking switches, and a gateway that routes between providers can put the others on cooldown for it: run such an endpoint through a local gateway. When the server answers 429 with `Retry-After`, every request waits that long. A reply with no grade in it is asked for once more. A pair that still has no grade, or that fails, is not written, and the next run tries it again. After 10 failures in a row the run stops and says why. Without `--corpus own`, `label` reads only the public library and queries, so nothing private goes to the judge: the private grades are the public ones, carried over by `generate`.

The prompt is `umbrela-akm-v1`, from our lab's earlier retrieval harness: one asset at a time, with its type, ref, name, description and the first 16,000 characters of its text (the harness read 1,500, which is too little for this library: most assets are longer). That is up to about 5,000 tokens, and 244 of the 259 assets fit whole. Grading all 1,521 pairs took 78 minutes on one local GPU. Grade 3 is exactly the asset an agent should load. 2 is relevant and clearly useful, though not the best. 1 is the same topic but would not help with this query. 0 is unrelated.

Run it again after a change to the library or to akm. The pool takes in the new top 10, and only the pairs that are new get a grade.

`--corpus own` grades your own set the same way, with these differences. Your notes go to the judge, so it refuses to run unless the judge model's line in `models.json` says `"private": true`, a model that you run or whose provider does not keep or train on what it gets. Nothing is inferred from `JUDGE_BASE_URL`, its host or the model's name, and a gateway model with no line is refused. The pool is the top 10 of `akm search` and of `akm curate` over the bundles, with no BM25 and no expected assets: akm lists 200 assets for a call, so `label` cannot list a library of tens of thousands to run a BM25 over, and it knows an asset only by what akm returned for it. A query with `expected` assets stops the run for the same reason. The grades are appended to `private/retrieval/own/qrels.jsonl` in the rows it has (`id`, `ref`, `grade`, `reason`), and nothing is written to `assets/`. `label` reads 16,000 characters of an asset. Grades that another tool made with another window, prompt or judge do not mix cleanly with these (the library's grades moved on 19.5% of its pairs when the window went from 1,500 to 16,000 characters), so find out how a set was graded before you extend it.

## Notes

- Unjudged results count as not relevant in `ndcg_10`. The library's judgments cover what akm 0.9.26's keyword search and a plain BM25 returned in their top 10, and what the author expected. A run on another akm version can return assets nobody graded, and so does the semantic search: 71% of its top 10 on the library was judged, against 100% for keyword search. Its library scores are therefore lower bounds, and the keyword and semantic columns are not on equal terms there until the semantic results are graded too. Any change of a ranker or a config that surfaces assets nobody graded is penalised for surfacing them, which favours the status quo. `judged_10` shows how large a share of the results is unjudged, and `ndcg_10_condensed` (nDCG over the judged results alone) is the other bound: the real score lies between the two, and when they are far apart neither can say whether a change helped. When `judged_10` falls, run `label --from <the run>` before you compare (`label --corpus own --from <the run>` for your own set), and then run again. The pool of plain `label` is the keyword results only.
- The books' judgments name only the relevant assets and the banned ones of each query. Every other asset counts as not relevant, though some may answer a query, and `judged_10` reads about a quarter. They are goldens, not a pooled test collection. `label` does not touch them.
- The judge reads the first 16,000 characters of an asset. The 15 assets that are longer are cut there, and an answer past the cut is not seen.
- Compare results only between runs with the same akm version, embedding model and judgments. For the semantic columns of the public library, also the same filesystem. For each of the 17 refs that two files of the library claim, akm indexes the file it reads first, and the filesystem decides that order ([akm#1050](https://github.com/itlackey/akm/issues/1050)). Two indexes of the library, one in a temporary folder on tmpfs and one on the disk of the cache, backed those refs with different files. They gave the same top 10 in the same order for 58 of the 136 queries with semantic search, and the same set for 105, and nDCG@10 0.798 against 0.806. With the second files removed, the two indexes ranked all 136 queries the same. The keyword columns and the books did not change. The eval keeps its semantic index in one folder, so its own runs are comparable.
- A much better public score than private score would point to akm having been tuned to the public names, tool names or numbers. The library's private copy changes about 1.6% of the words (3.5% when every tool is renamed), 3.1% of the queries' and 29 of its 245 graded refs, with akm and the tools the library runs kept: see above, and `private/retrieval/map.json` for every name it renamed. It is a light perturbation, not held-out data. Renamed words also change the keyword statistics a little, so a few results in places 4 to 10 differ between a public and a private run, and `judged_10` can read slightly under 100% in the private run. The books' private copy changes under 1% of the words, so it tests this much less: with akm 0.9.26 it scores exactly like the public books.
