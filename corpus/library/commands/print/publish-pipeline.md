Run the complete TTRPG publishing pipeline for `$ARGUMENTS`.

Treat `$ARGUMENTS` as:
`<content-path> [--entry <manifest-or-entry>] [--output <pdf>] [--engine <gutterpress|pdfx>] [--trim <size>] [--assets <dir>]`

If an optional value is omitted, inspect the repo for the most likely default and state the assumption before continuing. If a required input cannot be determined, stop with `NO-GO` and report the exact missing path or flag.

## Operating Rules

- Execute phases in order.
- Record the command used, the artifact produced, and the gate result for every phase.
- Stop immediately on any phase that returns `NO-GO`.
- `FIX` means the phase found issues but later phases may still run.
- Build the PDF during this command when inputs are available; do not stop after Phase 2 just because the PDF does not exist yet.
- When summarizing, use the reports generated by the current run or the newest matching artifact if the tool reuses an existing report.

## Phase 0: Resolve Inputs

Before running the pipeline, resolve and print these working values:

- `CONTENT_PATH`
- `ENTRY_PATH`
- `OUTPUT_PDF`
- `ASSETS_DIR`
- `TRIM_SIZE`
- `ENGINE`

Also verify `gutterpress doctor` reports the tools this pipeline needs (a Chromium-based browser always; `gs` and `qpdf` for PDF/X output), and that `skills/print/print-utilities/scripts/compare-pdf.ts` exists for Phase 5.

If `.reviews/` is missing, create it.

## Phase 1: Content Validation

```bash
gutterpress validate --input <content-path> --category source --skip source.accessibility.* --format json
```

- Gate: `GO` or `FIX` only
- `NO-GO` if rendering-breaking errors are reported
- Covers markdown lint, local link/image refs, layout markers, and merge markers.
  Accessibility is skipped here because Phase 2 runs it on its own.
- Markdown linting only runs when the project has a `.markdownlint.*` config (or
  `validate.source.markdownlint` set in the manifest); without one that check
  reports nothing.

## Phase 2: Accessibility Check

```bash
gutterpress validate --input <content-path> --only source.accessibility.* --format json
```

- Gate: `GO` or `FIX` only
- `NO-GO` if unresolved CRITICAL accessibility issues are reported
- Artifact: `.reviews/check-accessibility.*.md`

## Phase 3: Build PDF

```bash
gutterpress build <entry> -o <pdf> --format <pdf|pdfx>
```

- Gate: `GO` only
- `NO-GO` if the PDF is not generated successfully
- Artifact: `.reviews/build-pdf.*.md`

## Phase 3.1: Asset Audit

```bash
gutterpress audit <assets-dir> --format json
```

- Gate: `GO` or `FIX`
- Keep running on `FIX`, but unresolved RGB or low-DPI assets prevent an overall `GO`
- Artifact: `.reviews/audit-assets.*.md`

## Phase 4: Technical Preflight

```bash
gutterpress preflight --pdf <pdf-path> --target dtrpg
```

- Gate: `GO` only
- `NO-GO` on any technical print blocker
- Checks: PDF/X, fonts, TAC, signature alignment
- Artifact: `.reviews/preflight-print.*.md`
- Trim size and TAC limits come from the manifest's `preset`/`page`/`ink` keys, not from CLI flags here.

## Phase 5: Visual Review

```bash
bun run skills/print/print-utilities/scripts/compare-pdf.ts <baseline-pdf> <pdf-path>
```

- Gate: `GO` or `FIX`
- `NO-GO` only if the review identifies a release-blocking visual defect
- HIGH issues are acceptable for proofing but not for final upload
- If the visual review depends on a missing baseline or setup, report `FIX` with the exact missing prerequisite instead of inventing a `GO`
- Checks: layout, typography, tables, margins
- Artifact: `.reviews/dc.review-pdf.*.md`

## Phase 6: Final Decision

Synthesize the phase artifacts into a single recommendation.

Overall status rules:

- `NO-GO`: any phase returned `NO-GO`
- `FIX`: no `NO-GO`, but unresolved blockers or release-preventing issues remain
- `GO`: all required phases passed and no unresolved CRITICAL/HIGH/technical blockers remain

Generate or update a final status artifact at:

- `.reviews/generate-report.*.md`

## Required Output

Return:

1. `Overall Status`: `GO`, `FIX`, or `NO-GO`
2. `Resolved Inputs`: the final values used for content, entry, output, assets, trim, and engine
3. `Phase Summary Table` in this format:

| Phase | Status | Artifact | Blockers |
|---|---|---|---|
| Content | GO/FIX/NO-GO | path | count/summary |
| Accessibility | GO/FIX/NO-GO | path | count/summary |
| Build | GO/FIX/NO-GO | path | summary |
| Asset Audit | GO/FIX/NO-GO | path | count/summary |
| Preflight | GO/FIX/NO-GO | path | count/summary |
| Visual | GO/FIX/NO-GO | path | count/summary |

4. `Top Blockers`: up to 5 items with phase and artifact reference
5. `Next Actions`: exact fixes required before proof or upload
6. `Release Recommendation`: one of `proof-ready`, `fix-then-proof`, or `do-not-upload`

## Example Invocation

```bash
# content/ = markdown source directory
# content/manifest.yaml = print entry file
# dist/book.pdf = rendered PDF output
# 6x9 = trim size
/print/publish-pipeline content/ --entry content/manifest.yaml --output dist/book.pdf --trim 6x9 --engine gutterpress
```
